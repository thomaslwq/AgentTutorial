# ch09-rag-advanced-eval · 第 09 章配套示例

两个脚本：`query_rewrite.py` 演示查询改写、多查询扩展、HyDE、子问题分解；`rag_eval.py` 用纯标准库计算命中率、召回率与 MRR，不依赖 ragas。

## 环境准备

```bash
export OPENAI_API_KEY=sk-你的key   # 可选；query_rewrite.py 未配置时走离线兜底
# 兼容 OpenAI 协议的国产服务另设：
# export OPENAI_BASE_URL=https://your-endpoint/v1

pip install -r requirements.txt
```

> `rag_eval.py` 只使用 Python 标准库，不装任何依赖也能直接运行。

## 运行

```bash
python query_rewrite.py   # 四类查询增强策略的输出对比
python rag_eval.py        # 打印 Hit@1、Hit@3、Recall@3、MRR 与逐条明细
```

## 预期输出

`rag_eval.py` 内置 5 条标注用例。其中前 4 条相关文档都在召回列表内，第 5 条未命中；运行后可看到：

- `Hit@1` 低于 `Hit@3`：只看第一名时排第二、第三的相关文档不计入；
- `MRR` 介于倒数排名之间：第一条相关文档排第 1 得 1.0，排第 2 得 0.5，排第 3 得 0.33；
- 未命中用例的 RR 为 0，会把 MRR 拉低。

`query_rewrite.py` 在配置 Key 后，会对同一个差旅报销问题分别给出规范改写、多条同义查询、一段假设答案（HyDE 输入）和拆分后的子问题；未配置 Key 时各分支原样返回问题，仅用于验证流程不报错。

## 指标口径

| 指标 | 计算方式 | 衡量什么 |
|---|---|---|
| Hit@k | 前 k 条至少命中一条相关文档的用例占比 | 「有没有找到答案」，不关心命中几条 |
| Recall@k | 前 k 条命中的相关文档 / 全部相关文档 | 相关信息被覆盖得全不全 |
| MRR | 第一条相关文档排名倒数的平均值 | 相关文档排得够不够靠前 |

答案侧指标（答案是否忠于检索资料、是否切题）需要大模型参与评判，是 RAGAS 一类框架的范围；本示例先把检索侧指标跑通，接入框架与线上埋点见第 13 章。

## 练习参考答案

### 练习 1：改动评测集观察指标变化

打开 `rag_eval.py`，把第 5 条用例的 `retrieved_ids` 改为 `["doc-2", "doc-3", "doc-1"]`（让 `doc-2` 排第一）。重跑后 `Hit@1`、`Hit@3`、`MRR` 都会上升：该用例 RR 从 0 变为 1.0，Recall@3 从 0 变为 1.0。这说明指标对「相关文档是否被召回、排在第几」非常敏感，调检索策略前后必须用同一套评测集对比。

### 练习 2：多查询结果合并召回

`expand_multi_query` 返回多条同义查询后，把每条查询分别送进第 08 章的 `HybridRetriever.retrieve`，把各路返回的文档按文档 id 合并：同一篇文档在多路出现就累加 RRF 分（或记录出现次数），再按合并分排序、去重截断。这样能覆盖不同表述下的召回，但查询条数增加会放大检索与嵌入成本，通常取 2–3 条即可。

### 练习 3：召回率高不等于答案好

检索命中只是答案正确的必要条件。常见断点包括：相关文档被切散在多个块里、上下文中混入低相关片段稀释注意力、模型脱离资料自由发挥（不忠实）、子问题答案未正确汇总。因此 RAG 评测要分两层：检索侧看 Hit/Recall/MRR，生成侧看答案忠实度与切题度；只调检索指标，不能保证最终答案质量。
